# 测试阶段增量存档设计

## 用户目标与已确认范围

只有发生变化的数据才写入存档。水分变化不重写背包、采集记录或地形；采集一个点只写新增的采集身份及实际变化的物品、任务字段。用户已确认采用“初始快照＋变化记录”，测试阶段不兼容旧格式、不迁移旧存档。已有旧文件保留，旧格式明确提示需要新建游戏。

本次属于存档结构调整，已按用户“直接做，不要计划”的指示完成实现。使用当前本地工程及 Unity MCP；未新建 worktree、提交或打包。

## 修改前实现与证据

- `SaveSystem.MarkDirty(reason)` 只设置整体 dirty，并从最后一次标记开始等待 0.5 秒；`Flush` 同步捕获并写入整个活动域。采集等事务也会立即调用 `Flush`。
- `SaveSystem.Flush` 先克隆远征 DTO，再克隆河谷布局覆盖原布局，保存成功后 `SaveModel.SetExpedition` 再克隆一次。
- `SaveFileStore.SaveDomain` 全量校验、缩进 JSON 序列化、写临时文件、回读解析整个 JSON，然后替换正式文件。
- 同一河谷数据副本的三次分阶段测量：66,049 个高度值，约 3,460 个布局点，JSON 约 2.2 MB；序列化 119～177 ms，回读解析 139～190 ms，实际写文件 5～6 ms。完整回调采样此前捕获 `SaveSystem.Update` 325.239 ms。
- `IScopedSaveSectionProvider` 已提供分区捕获、验证、恢复及基地/远征/共享玩家范围。世界记录已有 RuntimeId，物品格有 Index，采集点有稳定字符串 ID，可以复用这些身份。

以上为 Unity Editor 测量，不代表目标设备或后台写入的性能保证。同步文件写入仍可能受设备存储影响。

## 方案与职责

### 保留领域模型，替换持久化方式

Model 继续保存权威业务状态，System 继续控制规则和事务。`SaveSystem` 负责收集候选变化、领域校验、保存成功后的基准推进，以及失败后的脏状态保留。`SaveFileStore` 负责新格式、原子记录、读取重放、文件身份和损坏判定；不访问 Unity 对象或决定业务状态。

`IScopedSaveSectionProvider`、现有 `MarkDirty(reason)` 和同步 `Flush(out error)` 保留。调用者无需通过解析 reason 字符串来决定数据身份。首次实现使用已有分区捕获，比较当前可变状态和上次成功提交的可变状态，仅生成实际差异；捕获完整小分区不等于将完整分区写入磁盘。

普通 Flush 的候选捕获不包含 `ValleyLayout`，不克隆、序列化或逐高度比较地形。当前远征布局进入时确定，正常游戏不会修改地形清单；改变远征身份必须新建初始快照。未来若新增地形编辑，需要另行设计明确的变化入口。

### 新建快照与存储身份

在 `Saves/incremental-v1/` 内保存新格式，每个活动域使用固定入口描述文件，指向独立 generation。generation 包含：存储格式版本、域、存档身份、地图身份，以及完整初始快照和变化日志。远征身份使用 ExpeditionId；基地创建独立稳定存储身份；运行时 MapInstanceId 不持久化。

新建基地、首次保存新远征时允许写完整初始快照。先写入并验证新 generation，再原子发布入口描述文件。失败不得替换当前可读取的 generation。原快照在该 generation 生命周期内不可变；普通保存不改写它。

当前 `ExpeditionFlowSystem` 在新河谷完成生成、安装布局并捕获分区之后才首次 SaveExpedition，因此首个快照已包含完整布局。普通 Flush 缺少有效新格式 generation 时返回需要新建游戏，不把编辑器中残留的旧格式运行态偷偷保存为新格式。更新代码后的人工验收从新建游戏开始。

同一存档后续的 `SaveBase`、`SaveExpedition`，包括结算或状态提交，走差异提交，不因为调用了这些公开方法就再次写初始快照。保存给定 DTO 与普通 Flush 共用差异协议，避免出现第二个全量写入入口。

### 变化粒度

| 数据 | 记录方式 |
| --- | --- |
| 水分、体力、生命、计时、任务字段 | 变化字段的新值 |
| JObject 分区 | 属性增、改、删；区分 null 和删除 |
| 玩家背包、仓库、搜索容器物品格 | 容器身份＋格子 Index，新增/修改格的变化字段，清空格为删除 |
| 已采集点、科技、线索、捷径、已结算远征等 ID 集合 | 对应集合新增或移除的稳定 ID |
| 玩家、敌人、掉落、建筑、搜索容器等世界记录 | 类型＋RuntimeId；新增记录、变化字段或删除记录 |
| 固定顺序的小数组 | 按索引产生差异，长度变化显式记录；恢复时保持原语义 |
| 地形与初始资源定义 | 只在初始快照内，不进入普通变化日志 |

已知带身份的集合必须明确配置身份规则；不能把任意数组都当成集合，也不能用列表当前位置代替世界实体身份。新对象需要完整初值，已有对象只保存变化字段。变化记录包含期望旧状态或对应上一提交版本，拒绝对错误基准应用。

同一字段在 0.5 秒等待期间多次改变，Flush 时仅写最新值。若状态改回已提交值，不产生该字段的变化；无实际差异不写文件、不单独更新时间戳。存在真实变化时才随事务更新 UpdatedAtUtc。

### 日志提交与中断恢复

每次 Flush 是一条事务，包含格式版本、generation/域身份、连续序号、事务 ID 和本次全部变化。采集对应的“背包增加＋资源耗尽＋任务变化”一起提交；不能分成多个独立成功的字段写入。

日志采用有边界的追加记录：固定标记、有效载荷长度、长度的按位反码、UTF-8 紧凑 JSON 载荷、完整性摘要、结束标记。长度反码防止完整记录的长度损坏被误认为正常半写尾部。载荷只含差异；不回读解析整个初始快照，也不把全部既有日志重新写一遍。追加成功并刷新文件后才确认提交、推进序号和内存基准。

写入前记住上次完整记录边界。追加失败须回退到该边界，保留脏状态；回退也失败时，将存储标记为需要重新检查，禁止盲目再次追加。对写入结果不确定的事务，先读取尾部并按事务 ID 核对：完整且有效的同一事务应按已提交处理；未提交才继续重试。不得把已提交的采集报告为失败后又回滚运行态。

重放要求身份一致、序号连续、摘要有效、操作合法。尾部没有完成标记的残缺记录视为未提交，恢复到此前完整事务并报告尾部恢复情况；完整记录的摘要错误、身份不符、跳号或中间损坏视为损坏，不跳过后继续恢复，也不自动生成默认数据。

成功写入整条记录不代表任意断电场景下绝对耐久；保留已有错误返回语义，并通过故障注入验证软件可控的写入中断和结果核对。

### 读档、备份与生命周期

读档先验证入口及初始快照，然后顺序应用完整事务，最后执行现有领域、世界和河谷探索一致性校验，再进入现有候选地图/运行态提交流程。仍返回独立 DTO，读取对象不共享业务可变引用。

入口描述文件保留上一有效版本用于发布中断恢复。备用入口仅用于同一发布流程；不能因日志中间损坏而静默倒退到更早游戏状态。读取结果应区分不支持格式、损坏以及恢复了未完成尾部。

正常保存成功后更新已提交可变基准，不能再调用包含整张地形克隆的 SetExpedition 完成每次自动保存。初始创建、读档、切图事务和显式运行态回滚需要完整独立快照时，仍保留现有隔离语义。

`SaveRuntimeSnapshot` 保留待保存标记与计时时刻；已提交身份、序号与可变基准由存储适配器持有。恢复运行态不会撤销已经写入的日志；结算、死亡、返回流程继续按原有磁盘提交及幂等规则执行，不能以运行态回滚假装磁盘事务未发生。

删除远征覆盖新格式入口及其 generation；新建下一远征不会串入上一远征日志。只处理明确属于新存储目录的文件。基地与远征分别持久化，保持目前的跨域结算流程，不宣称两个域的多个文件有额外的全局原子性。

测试阶段先不增加定时全量压缩，也不在普通保存时合并日志。日志随游戏时长增长，读档成本随记录数量增长；本次验证包含长日志重放。后续如需要压缩，单独设计加载界面中的维护流程。

## 旧格式与界面

新存储目录不存在有效入口、但发现旧固定存档时，返回“测试版本不支持此旧存档，需要新建游戏”，不读入、不迁移、不调用旧槽清理去删除它。

开始界面允许旧格式情况下新建游戏，隐藏不可用的继续入口并通过已有提示能力说明原因；不修改 Prefab 布局或生成 View。后续创建新格式成功后，以新格式为唯一有效来源。新格式损坏仍走损坏处理，不能误当旧格式或无存档。

旧格式探测只用于还没有新格式基地入口的初始状态。新格式基地创建成功后，新的远征入口不存在就是“没有待处理远征”，不能因为旧目录仍有 offline-expedition.json 而阻止开始新远征。新远征入口必须绑定其所属基地存储身份，新建下一游戏后旧 generation 不得成为可继续的候选。

玩家状态分区、背包风险规则、物品成本、任务、采集、地图布局和操作手感保持现有业务语义。只替换持久化协议和旧格式入口处理。设置与街机的独立存储不在本次范围内。

## 修改落点与验证

- `System/Save/SaveSystem.cs`：可变候选、差异事务、已提交基准、脏状态和运行态快照恢复；兼容原有同步事务调用。
- `Utility/Save/SaveFileStore.cs` 及项目自有的窄存储辅助类：格式、差异协议、原子发布、日志、读取重放和删除。
- `Model/Save/SaveGameData.cs`、`SaveModel.cs`：读取状态/存储身份、成功提交后的可变快照更新；保持模型不直接写文件。
- `StartUICtrl` 及现有启动恢复消费者：旧格式提示、新建入口和新格式恢复；若新增提示键，走正式本地化源流程，不手改生成代码。
- 同步更新存档主题文档；本次涉及的核心类、关键函数和重要字段补充简洁中文职责和失败语义注释。

实施按先协议和失败测试、再存储、再 SaveSystem、最后入口接线执行。先人工自审，不启动子代理，不自动提交。

定向测试须覆盖：无变化不写；单字段记录不含无关字段/布局；物品格清空、实体删除、ID 集合增删；同事务多个分区同时恢复；重复事务不重复应用；保存失败脏状态保留；不确定结果核对；末尾半写恢复；完整记录损坏和身份错误拒绝；域与远征 generation 隔离；旧格式不迁移不删除且可新建；采集回滚、返回结算和死亡恢复不改变；长日志重放。

先统计并选取精确类或方法，所有 Unity 测试声明最大执行数量、使用 includePassingTests=true，核对返回名称和实际执行数。不运行完整套件、不只用 namespace/assembly 过滤、不触发 Player Build。

性能验收重新进入新建河谷：记录普通保存载荷字节数、主线程 Flush 耗时、阶段耗时和尖峰；确认单次玩家状态变化不包含高度数组/未变资源清单，不改写初始快照。不能仅凭测试通过或小文件推断画面已完全无卡顿；报告站立、走动与采集的实测结果及设备限制。
