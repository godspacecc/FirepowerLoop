# 代码与测试规范

## 1. 用途与适用范围

本文是 AnotherDay 手写客户端、服务端、工具和测试代码的统一规范入口。它解决“规则散落在路线图、知识文档、测试源码和历史计划中”的问题，不替代各功能专题中更细的业务合同。

本规范对新增代码和被实际修改的代码生效。既有代码不因命名、空行、字段前缀或文件长度不同而被批量翻修；但已确认的生命周期、并发、事务、资源、存档、玩家消息或测试证据缺陷不属于“历史风格”，应按风险单独设计和整改。

## 2. 规则层级

规则冲突时按以下顺序判断：

1. 已确认的产品行为、数据和协议合同。
2. 数据一致性、失败恢复、资源释放、生命周期和安全规则。
3. QFramework、Unity、ET、Luban、MemoryPack 和其它已采用工具链的有效约束。
4. 本文的项目职责和测试规则。
5. 命名、排版和个人风格建议。

不得为了满足低层风格规则而削弱更高层级合同。自动规则与已确认行为冲突时，先判定规则是否过宽或过时，不得仅为让测试变绿而曲解生产代码。

## 3. 源码边界

### 3.1 手写产品代码

- 客户端主要指 `Client/Assets/Game/Scripts/` 中排除生成与第三方目录后的代码。
- 服务端业务代码主要指 `Server/GameServer/Runtime/Model/Server/Online/` 与 `Server/GameServer/Runtime/Hotfix/Server/Online/` 等项目业务目录。
- 手写代码必须遵守本文的职责、生命周期、异步、错误和测试规则。

### 3.2 生成代码

- Luban 生成的 C#、`.bytes` 和协议生成物只能由权威源与生成入口重建，不得手改。
- 生成代码不需迎合手写代码的格式与文件长度建议。
- 测试应验证源、生成入口和运行时消费合同，不得用手改生成物解决问题。

### 3.3 第三方与框架代码

- `ThirdParty`、KCP、ET Core/示例基线、Luban Runtime 和 QFramework 基础实现不做无关格式化或批量重命名。
- 必须修改第三方或框架代码时，先证明不能在项目边界层修复，并保持可审查的最小差异。
- 不得把 ET 示例结构、客户端网络壳或未启用传输当成当前产品职责。

## 4. 客户端职责规范

### 4.1 Model、System、Controller 和 View

- `AbstractModel` 保存持久或领域权威状态；对外优先提供只读快照，不暴露可变内部集合。
- `AbstractSystem` 负责规则、状态转移、持续更新和领域事务。
- `IController` 或 ViewCtrl 负责创建、组装、资源准备、Unity 运行时端口与表现对象生命周期。
- `MonoBehaviour` View 只承担序列化引用、Unity 组件回调和表现，不保存第二份权威业务状态。
- UI 和输入层提交用户意图，领域所有者验证并修改状态。

一项职责只保留一个权威写入入口。事件必须在权威状态修改后发布，且携带稳定 ID 或不可变快照，不把 `GameObject`、`Transform`、View、资源 Handle 或可变协议对象当作领域事实。

### 4.2 公共生命周期

- `GameStart` 是 Unity `Update/FixedUpdate/LateUpdate` 到项目 `LifeCycle` 的公共桥接。
- 产品类不得仅为获得逐帧回调而新增 `MonoBehaviour`；持续职责应由实际所有者接入 `LifeCycle`。
- 每个 `RegisterUpdate/RegisterLateUpdate/RegisterFixedUpdate` 必须在同一所有者的释放路径中有对应解除。
- 事件、Unity 回调、计时器和输入回调也遵守“注册者负责解除”；依赖对象销毁自动解除时，必须能明确指出该销毁对象。
- `OnInit`、`OnDeinit`、`OnShow`、`OnHide`、`OnUnload`、地图卸载和应用退出是不同生命周期，不得互相代替。

### 4.3 地图、资源与异步创建

- 地图所有对象必须明确 `UnitId`、`MapInstanceId`、所有者根、权威、活动状态和释放路径。
- 可见修改前先验证配置和依赖。异步等待前捕获取消/generation 和预期 `MapInstanceId`，等待后重新校验。
- 候选对象先保持隐藏，验证 Prefab、组件和 NavMesh 合同后再提交到权威域。
- 事务失败时只逆序撤销已完成步骤；重复请求、事件、结算和释放必须幂等或明确拒绝。
- 每个资源 Handle 只有一个所有者和一条释放路径，覆盖取消、晚回调、回滚、替换、地图卸载和架构释放。

### 4.4 异步入口

- 可等待的内部操作返回 `UniTask`、`UniTask<T>`、`Task` 或 `Task<T>`。
- `async void` 只允许作为 Unity/委托签名确实要求 `void` 的薄入口。它必须立即转调可等待方法，不直接承载多步事务。
- `.Forget()` 只用于明确的 fire-and-forget 边界；被调方必须处理预期失败，未预期异常必须进入项目日志或统一异常处理。
- UI、地图和联机操作在等待后必须重新校验所有实例、显隐状态、请求 generation、连接 generation 或地图身份。
- 预期取消不记为产品错误；真正失败不得留下永久忙碌标志、失效按钮、半提交状态或无所有者资源。

## 5. UI 代码规范

- 独立窗口使用 `BaseUICtrl + BaseUI`，宿主内嵌页使用 `BasePageCtrl`，复用行或小元素使用 `BaseBoxUI`。
- Prefab 保存稳定层级、锚点、尺寸、布局、字体、材质和序列化引用；Controller 不复制静态布局。
- 必需序列化引用缺失是 Prefab 合同错误，不得用沉默空判断跳过功能；真正可选引用必须在 View 合同中明确。
- `OnInit()` 对每个加载的 View 实例运行一次，适合绑定 View 拥有的按钮和列表回调。能超过 View 存活的订阅必须有明确解除所有者。
- `OnShow()` 重绘当前权威快照；`OnHide()` 清理可见性所有的焦点、拖动、计时和短期工作；`OnUnload()` 不访问已销毁 View。
- 内联 lambda 不做“全项目无条件禁止”。需要精确解除、可能重复绑定、可能超过 View 存活或需要单独测试的回调必须使用稳定方法或保存可解除委托；仅由当前 View 拥有、只绑定一次且随 View 销毁结束的简单参数适配可使用 lambda。
- 玩家可见文本使用本地化入口。不向玩家直接显示异常消息、技术错误、路径、堆栈、内部 ID 或服务端原始文字。
- 在正式本地化程序集和玩家语言设置尚不可用、且产品当前只发行一种语言时，Boot 前置界面可以使用当前发行语言的集中式固定文案；该例外不得引入对 Game 本地化的反向依赖，文案必须由稳定错误码统一映射，业务逻辑不得判断显示文字。产品确定多语言发行后，Boot 必须改用独立于 Game 加载结果的本地化来源。
- 稳定角色、ID、枚举和快照作为业务数据；不用本地化显示文字分支业务逻辑。
- 循环列表或对象池复用元素时，每次刷新覆写全部文本、图像、显隐、可交互、选中、ID 和回调状态。

## 6. 配置、协议与存档

- 运行时配置通过 `IRuntimeConfigProvider` 或所属服务端配置入口读取，不在 System、View 或测试中复制默认值绕过配置。
- 协议、Luban Schema/CSV 和生成入口是不同责任。必须修改权威源并通过既有入口生成，不得只改一侧生成物。
- 存档只保存稳定领域值和 ID，不保存场景对象、Unit、Transform、Context、Handle、协议对象或临时 UI 状态。
- 存档格式改变必须明确版本、迁移、失败恢复、原子写入和旧数据证据，不得用默认值静默吞掉损坏状态。

## 7. 服务端代码规范

- 继续使用 ET 自带分析器实施 Entity、System、Handler、`ETTask`、取消和组件访问约束；本文不复制或放宽 `ET0001`～`ET0032` 的编译期语义。
- Model 保存 Entity/组件数据，Hotfix System/Handler 执行行为；不为方便把新业务逻辑放回 Entity 或 Gate 代理。
- Actor/Fiber 职责必须有唯一写入权威。跨 Actor 事务明确候选、提交、回滚、幂等、超时、旧 Epoch/generation 丢弃与释放顺序。
- 外部 Handler 只接受当前白名单中的已认证请求；Gate 不保存本应由 Account、Player、Room 或 World 拥有的权威副本。
- 日志不记录密码、Token、完整来源地址、协议对象或未清洗用户输入。可记录稳定 ID、职责阶段、错误码和脱敏摘要。
- 不对 ET 原生基线做全仓格式化，不为了统一外观改写示例或第三方代码。

## 8. 错误、日志与玩家消息

- 领域结果使用稳定状态或错误码表达程序分支；文字用于诊断和显示，不作为业务判断键。
- 除第 5 节明确的单语言前置界面例外外，玩家消息必须本地化；所有玩家消息都必须可行动且不泄露技术细节。诊断日志应包含职责类型、失败阶段、稳定 ID 和异常链。
- 不记录逐帧诊断日志；高频日志必须合并、限频或仅在明确诊断开关下启用。
- `catch` 不得静默吞掉异常。能转换为预期领域失败时返回稳定结果；否则保留完整异常用于诊断，并把运行时恢复到稳定状态。

## 9. 命名与格式

### 9.1 强制命名边界

- 类型、方法、属性、事件和公开字段使用 `PascalCase`。
- 参数、局部变量和新增私有字段使用 `camelCase`。既有 `_camelCase` 字段不做专项批量重命名。
- 布尔值名称应表达真实语义，优先使用 `Is`、`Has`、`Can`、`Should` 或明确状态词。
- 普通产品类型不增加无意义的 `AnotherDay` 前缀；外部协议、稳定数据 ID、历史稳定名称和多项目共享约束除外。
- 文件、主要类型和职责名保持一致。生成、partial、窄窄内部值对象或已确认框架模式可例外。

### 9.2 格式原则

- C# 使用 4 个空格缩进，不使用 Tab 混排手写代码。
- 大括号换行，文件以换行结尾，不保留行尾空格。
- `using` 优先保持 `System` 系列在前、同组按稳定顺序排列；不为排序导致大量无关差异。
- 使用 `var` 或显式类型以当前方法的可读性为准，不把二者之一设为全项目强制风格。
- 不因为新增 `.editorconfig` 而格式化本次职责以外的文件。

### 9.3 文件与职责规模

- 不设置机械的最大行数。手写文件超过约 500 行，或同时承担状态、事务、资源、UI 和网络中多个独立责任时，触发职责复审。
- 复审先判断是否存在多个权威、释放路径或事务边界，不为了降低行数而拆出无语义 Helper 或通用层。

## 10. 测试规范

### 10.1 验证分层

- 规则、状态机、幂等、结算、存档迁移、配置校验和失败回滚优先使用 EditMode 行为测试。
- Prefab/场景必需引用、唯一性、禁止组件和生成物物理边界使用少量静态合同测试。
- 移动手感、相机、UI 实际点击、物理、碰撞、渲染、音频和完整地图往返由人工 PlayMode 快速验收。
- 当前不新增 PlayMode 自动化。已存在的历史 PlayMode 烟雾测试保留但冻结，不作为新功能默认验证路径。

### 10.2 行为证据优先

- 行为测试通过真实公开入口触发，观察权威状态、稳定事件、对外端口、表现快照或释放结果。
- 按钮行为应触发真实 `Button.onClick`；生命周期应调用真实公开生命周期；失败恢复应由可控依赖产生真实失败。
- 不得用私有结果方法、手动设置内部标志或源码字符串断言替代可实施的行为证据。
- 源码字符串测试只保留给编译器和类型系统难以表达、且确实必须禁止的关键架构边界。规则必须有正反样例，不得因变量名、排版或合法的本地化结果而误报。

### 10.3 测试夹具

- 重复的架构重置、虚假配置、资源端口和网络时钟应逐步收敛到职责明确的共享夹具。
- 共享夹具修改必须先确认所有生产者和消费者。预计影响十项以上既有测试时，至少进行二级最小风险探针，不直接全量改写。
- 测试不得写入、覆盖或修复产品 Prefab、场景、配置或存档样本。
- 每项测试自己创建的 Unity 对象、事件、生命周期委托、临时目录和网络任务必须在清理阶段释放。

### 10.4 执行范围与证据

- 实施中只运行新增或直接受影响测试；返修中只运行失败项及直接相邻合同；最终收口时每个必要受影响类最多完整运行一次。
- 不用测试数量代替需求覆盖；实施结果必须记录实际 Mode、Filter、Status、目标范围、Passed/Failed/Skipped、Duration 和 Error Logs，工具未返回的字段不推测。
- 默认不运行全量 EditMode、PlayMode、Player 构建、正式资源构建或其它高成本验证，除非当前任务明确要求。

## 11. 编码规则的自动化边界

- 编译器、ET Analyzer 和 `.editorconfig` 适合检查可稳定语法化的规则。
- EditMode 编码规则测只检查项目特有且不能由编译器表达的关键边界。
- 需要理解职责、事务、玩家语义或失败恢复的规则属于代码审查，不用宽泛正则强行替代。
- 自动规则新增或修改时必须同时提供应拒绝、应允许和真实项目样例，并先检查当前同步代码的实际命中面。
- 不得在一个规范整改中同时将大量历史建议升级为阻断错误。

## 12. 修改代码时的最小自审

每次修改手写产品代码时，至少回答：

1. 权威状态和写入入口在哪里？
2. 新增订阅、逐帧回调、计时器、资源和 Unity 对象由谁释放？
3. 异步等待后如何丢弃旧实例、旧地图、旧连接或旧请求结果？
4. 失败时稳定状态是什么，哪些已完成步骤需要逆序回滚？
5. 玩家看到的是本地化可行动消息，还是内部技术文字？
6. 测试是否通过真实入口证明行为，还是只证明了源码长得像预期？
7. 实际变更是否仅限本次职责，且没有手改生成物或格式化无关文件？

## 13. 已知治理顺序

本文建立不表示当前所有代码已符合规范。已确认问题按以下顺序另行设计和处理：

1. 精确化 UI 编码规则，消除已确认误报，并修复真实的本地化与技术错误泄露。
2. 将仅为联机运行时 `Update()` 存在的产品 `MonoBehaviour` 收敛到公共生命周期。
3. 从高风险入口开始收敛 `async void`/`UniTaskVoid`、请求过期与异常恢复。
4. 增量提取共享测试夹具，减少重复架构重置、宽泛反射与源码字符串断言。
5. 手写大文件只在职责边界确实分裂时拆分，不进行按行数的全项目重构。
