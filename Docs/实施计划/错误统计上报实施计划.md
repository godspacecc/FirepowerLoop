# 错误统计上报实施计划

> 状态：用户已确认并进入实施。实际完成项与受阻项以实施结果记录为准。

> 2026-10-01 用户确认局域网使用方式调整：同一 Wi-Fi 测试采用 `LocalGameServer` 模式，从已保存的联机地址（无覆盖时取包内 networkConfig）选择同一电脑的 HTTP 31002；保存/重置地址后同步刷新并保留历史队列，启动后无需登录即可补传。只接受内网 IPv4/回环地址。公网采用固定 HTTPS `Fixed` 模式，不随联机地址变化。本修订覆盖下文原首版 ERR-01 的固定地址隔离要求，以及对应效果、实施步骤和验收中仅允许固定地址的描述；队列格式、脱敏、保留、服务端协议与限流保持原约定。实际 Android 包需由用户手动打包并覆盖安装。

## 目标与范围

让离线和联机游玩中的关键程序错误默认进入同一有界待上传队列，经独立诊断 HTTP 入口匿名发送至游戏服务器并按日期、版本、平台和错误指纹统计。设置网络页提供“清理待上传记录”，不提供关闭上报开关。上传故障不改变启动、游戏、存档、联机或资源下载结果。

首版覆盖 `Launcher.ShowFailure` 已归类的 Boot 失败，以及 `RuntimeLogSystem` 收到的 `Error`、`Exception`、`Assert`。Boot 入口建立前的异常、原生崩溃、普通日志、Warning、完整日志远程查看、账号关联、管理后台和资源服务器修改不在范围内。

## 完成后玩家与运营侧的效果

- 玩家无论离线还是联机，发生上述程序错误后，客户端会自动合并、保留并择机上报匿名统计；没有可达诊断服务时会在限额内保留最多 7 天，容量满后可能丢弃较旧或新增的统计事件，不影响游玩。
- 上传只包含错误类别、指纹、版本、平台、UTC 日期和次数；Boot 另含错误码与阶段。玩家的完整本地错误日志仍可用于设备上排障，但不会随上报发送。
- 网络设置页可看到待上传组数并清理本机尚未确认的记录。清理不会关闭后续自动采集，也无法撤回服务端已经收到的请求；已有完整本地日志不会被清理。
- 游戏服务器把成功接收的批次保存到按接收日分文件的运行数据目录，最多保留 30 天；只读脚本按错误发生日、版本、平台和指纹输出合并次数，同一批次重试不重复计数。
- 本机开发默认地址仅能连接同机的 31002 端口。跨设备或公网正式使用需要在打包前配置实际 HTTPS 地址，并部署受控代理、来源 IP 传递和 31002 访问限制；服务端当前只在 `OnlineLocal` 配置启用诊断处理器，若以后改用 `Release` 配置部署，须另行确认并修订此范围。这些部署条件未完成时，客户端只排队，不会获得远端统计。

## 实施基线

- `Client/Assets/Boot/Launcher.cs` 的 `ShowFailure` 已持有 `BootFailure.Code` 和 `Stage`，`BootErrorLogStore` 保存最近一次完整失败信息；Boot 稳定程序集先于 Game 加载。
- `Client/Assets/Game/Scripts/System/RuntimeLog/RuntimeLogSystem.cs` 订阅 `Application.logMessageReceivedThreaded`，回调可能并发；Error、Exception、Assert 当前在回调线程即时写入有上限的本地完整日志，既有测试依赖此时序。新增上报采集不改变这条已有路径。`Game.cs` 注册该 System。
- `GameGate` 仅在玩家主动登录时连接；上报不使用 `INetworkRuntime`。`Server/ResourceServer/` 只提供 GET/HEAD 下载，不接受上传。
- 游戏服务器 `RouterManager` 已有 `HttpComponent` 和按路径分发的 `IHttpHandler`，监听前缀为 HTTP；`Config/DataCsv/server_start_scene.csv` 的 `OnlineLocal` 尚无 RouterManager 行。公网 HTTPS 需要受控反向代理与网络访问限制，不能把现有 RouterManager 误认为自带 TLS。`Config/gen.bat` 是 Luban 唯一生成入口；`TbStartScene` 只生成服务端数据。
- 设置的网络页由 `SettingNetworkPageCtrl`、`SettingNetwork.prefab` 和生成的 `SettingNetworkPageUI` 组成；Prefab 引用通过 Page UI 生成工具建立。`zh-CN.json` 与 `en-US.json` 提供玩家文案。

## 确定的实现规则

| ID | 实现规则 |
| --- | --- |
| ERR-01 | `Client/Assets/StreamingAssets/diagnosticConfig.json` 提供固定 `reportUrl`，不读取玩家可编辑的 GameGate 或资源服务器地址。`http://127.0.0.1:31002/diagnostics/errors` 仅为本机开发默认值：Android、其它电脑和正式发布包若未替换，访问的是玩家设备自身，不会送到游戏服务器。正式公网发布前必须将其替换为实际 HTTPS 地址，并检查目标部署已就绪；本计划不执行 Player 构建，发布检查由实际打包者完成。通过适配 StreamingAssets 的异步读取加载，Android APK 内路径不得按普通文件读取。配置缺失、无效或不可达时只保留本地队列，不中断游戏。只接受绝对 HTTP/HTTPS URL；非回环地址在正式配置中必须使用 HTTPS。 |
| ERR-02 | Boot 稳定程序集拥有唯一持久待上传队列与发送器，Game 复用它。`Launcher.ShowFailure` 每次实际失败只提交 `BootFailure.Code`、`Stage` 和采样时间，不读 `CopyDetails`；`RuntimeLogSystem` 的新增上报采集只接收 Error、Exception、Assert。日志回调中的新增采集只做线程安全的有限快照，不调用 Unity 主线程专用 API、不发送网络、不产生日志；现有 `RuntimeErrorLogStore.Append` 即时保存完整本地错误日志的行为和时序保持不变。新增快照队列满时允许丢失上报事件，不能阻塞或改变已有日志与游戏流程。 |
| ERR-03 | 每条统计记录只含 `source`（`Boot`/`Runtime`）、`kind`（`BootFailure`/`Error`/`Exception`/`Assert`）、`fingerprint`（小写 64 位十六进制 SHA-256）、`buildVersion`、`platform`、`eventDate`（UTC 发生日，`yyyy-MM-dd`）、`firstUtc`、`lastUtc`、`count`；Boot 另含 `bootCode`、`bootStage`，Runtime 这两项为空。`firstUtc` 和 `lastUtc` 必须属于 `eventDate`。指纹由来源、类别和 Boot 码/阶段或运行期调用栈在客户端计算；上传和队列文件都不保存原始日志正文、调用栈、路径、账号、密码、聊天、协议对象、存档、IP 或持久设备 ID。运行期调用栈为空时按来源、类别合并为一个无定位类别，不读取可能含敏感内容的消息补足。 |
| ERR-04 | 同一 `eventDate+source+kind+fingerprint+buildVersion+platform` 在客户端合并出现次数，不跨 UTC 日合并。持久队列（含未确认批次快照）最多 128 组、256 KiB，记录最多保留 7 天；满时先淘汰最旧的非批次组，仍放不下时丢弃新事件，不能改变未确认批次内容。单组累计次数使用有上限的整数并在上限饱和，禁止溢出。过期组及其未确认批次一起丢弃，不再重试；已到达服务器的旧请求仍可能被接收。写入用同目录临时文件加原子替换，损坏文件隔离后从空队列继续，任何 I/O 失败都不抛回游戏流程。完整本地错误日志不参与淘汰或上传。 |
| ERR-05 | 每次最多取 20 组组成一个不超过 16 KiB 的不可变批次快照，每组本次 `count` 取 1～10000；超过 10000 的累计次数分批发送。持久保存随机 `batchId`（UUID）、每组键、本次次数、时间字段及完整请求语义；重试复用相同 ID 和完全相同的内容，新错误仅增加实时队列次数并进入后续批次。只有当前有效批次的成功确认才按键扣除该快照次数，不能扣掉并发新增次数；迟到回调或已清理/过期的批次不得修改队列。一次只允许一个发送任务；超时 5 秒，失败后指数退避 30 秒至 30 分钟，避免逐帧或密集重试。成功和失败均不产生新的上报事件。 |
| ERR-06 | `POST /diagnostics/errors` 接受 `application/json` UTF-8 JSON：`schemaVersion=1`、`batchId`、`reports` 数组，元素字段严格为 ERR-03；其它方法返回 405。仅 1～20 条、请求体不超过 16 KiB。必须对 `Content-Length` 与分块/未知长度请求都实行实际读取字节数上限，超过上限返回 413；字段长度、重复或未知字段、枚举、`eventDate` 与 UTC 时间一致性、指纹、1～10000 的次数均严格校验，不接受原始文本。结构校验后先查询已持久 `batchId`：规范化字段内容相同的重复批次直接成功，内容不同的同 ID 请求返回 409；然后才对新批次限流、检查容量、持久追加到运行目录的 `Store/Diagnostics/yyyyMMdd.jsonl` 并刷新，最后确认成功。文件名按接收日，统计按 `eventDate`，同一 ID 只计一次。无效输入返回 400，新批次限频返回 429，存储不可用或容量已满返回 503，均不假称成功。处理器自行兜住诊断路径异常并明确写入 503，避免现有 HTTP 框架仅记录异常后关闭响应而让客户端误判。 |
| ERR-07 | 匿名入口按来源 IP 在内存中限为每分钟 60 次；限流状态最多保留 4096 个 IP，超过两分钟未活动的项清除，满表且无过期项时拒绝新来源并返回 429。直连时使用 `RemoteEndPoint`，不信任任意客户端提供的转发头；只有来源地址与显式配置的可信反向代理 IP 一致，且代理覆盖而非追加单值 `X-Real-IP` 头时才使用该头。可信代理转发头缺失、包含多个地址或无法解析时拒绝新批次，不能退化成所有玩家共用代理 IP 的限额。单日日志上限 32 MiB、每日最多 10000 个新批次，最多保留 30 天；IP 仅用于即时限流，不写统计记录。服务重启先扫描近期日志并恢复 `batchId` 去重集合；如末尾缺少完整换行，只能截断到最后一条完整有效记录的换行边界并完成持久修复，随后才允许追加。较早的完整行无效或尾部修复失败时拒绝新批次并返回 503，不能确认；截断批次由客户端用原 ID 重试。统计命令对同一 ID 再次去重并按 `eventDate+buildVersion+platform+source+kind+fingerprint` 汇总 `count`，只输出聚合结果。存储、解析、限流异常不得影响 GameGate、Room、World 或其它 HTTP 路由。 |
| ERR-08 | `OnlineLocal` 增加一个 `RouterManager` 场景，端口 31002，与 GameGate 的 31001 分离；沿用既有 HTTP 分发和启动配置索引，不增加联机协议、不要求玩家账号或会话，也不改资源服务器。处理器须检查当前服务配置为 `OnlineLocal`，在 `Localhost`、`Release`、`RouterTest` 等其它 `RouterManager` 配置一律返回 404，不读取请求体或写入统计。公网部署由反向代理对外提供 HTTPS，31002 仅允许受信任代理连接；代理必须覆盖单值 `X-Real-IP` 头并限制请求体大小，服务端只在显式配置 `DiagnosticTrustedProxyIp` 且实际 TCP 来源相符时采信该头。部署规则写入现有服务端部署文档并由人工配置防火墙/代理，本计划不自动改机器网络配置。本地服务器启动器预检 31001 和 31002，任一占用时不启动或结束现存进程。正式存储根固定为运行程序集目录 `Bin` 的上一级 `Store/Diagnostics`：源码运行位于 `Server/GameServer/Store/Diagnostics`，发布运行位于发布根 `Store/Diagnostics`，均不在会被发布清理的 `Bin`、`Config`、`Tools` 内；仅显式 `DiagnosticStoreRoot` 测试启动参数可改为隔离临时目录。 |
| ERR-09 | Boot 失败页存在时可尝试发送；`RuntimeLogSystem.OnInit` 只登记 Game 驱动候选，`Launcher.TryReportMainReady` 收到游戏就绪通知时，才在同一发送器内原子撤销 Boot 租约并授予 Game 租约。Launcher 在该通知后的下一帧才释放，交接不得依赖其销毁时机；若主场景初始化失败而未通知就绪，Boot 保持失败页发送权。无 Launcher 的 Game 测试入口可由 Game 直接取得租约。租约代次用于忽略旧驱动的晚完成回调，发送器始终只允许一个请求；Game 注销撤销自身租约。取消驱动或退出不删除未确认批次；下一次启动可继续。网络请求及完成回调不触碰已释放的 Launcher、View 或 System。 |
| ERR-10 | 设置网络页显示“自动上报程序错误”、待上传组数及“清理待上传记录”按钮，不提供关闭或诊断地址编辑。按钮点击调用队列权威清理入口：在同一同步边界内停止创建批次、删除待上传文件，删除成功后递增清理代次并取消当前请求；删除失败则保留可重试的队列并返回失败，不显示清理成功。晚到的旧请求回调因代次不符不能扣减清理后新采集的同指纹记录。保持完整 `boot-error.log`、`runtime-error.log` 与后续自动采集；已到达服务器的请求可能无法撤回，界面需明确说明。重复点击、隐藏重开、语言切换和 View 重载不重复绑定回调。 |
| ERR-11 | 上传功能只在有合法诊断地址且入口可用时发送。不存在服务端、离线、限流、超时、配置错误或日志写入失败时保持主流程可用；所有容量、时间、去重与失败路径不允许无限内存、无限文件或递归日志。 |

## 按依赖顺序实施

1. 在 `Config/DataCsv/server_start_scene.csv` 为 `OnlineLocal` 添加唯一 `RouterManager` 场景，使用未占用的场景 ID 108、原有 Process/Zone 键、端口 31002。通过 `Config/gen.bat` 重生成并只保留本次源变更导致的 `tbstartscene.bytes` 差异；在本地服务器启动器中同时检查 31001/31002 占用，诊断监听另需检查 URL ACL 可用。若已有同端口占用、生成器输出其它意外差异或场景初始化与现有 RouterManager 前提冲突，停止报告。
2. 在表列服务端两个新 C# 文件实现 ERR-06～08。启动时按 ERR-07 修复不完整尾部并恢复去重集合；修复失败不接受新批次。请求按方法与大小检查、严格结构校验、已持久 ID 与内容比较、新批次来源 IP 解析和限流/容量检查、持久写入并刷新、确认的顺序处理；重复同内容 `batchId` 不追加，包括限流与容量已满时。处理器检查 `ServerConfig.Instance.Profile`，非 `OnlineLocal` 返回 404。限流状态表按 ERR-07 设上限，可信代理来源仅使用显式 `DiagnosticTrustedProxyIp`，其默认值为空且直连时忽略转发头。保留其它 HTTP 路由的行为。统计脚本只读有效日志行，对重复 ID 去重并按 `eventDate` 输出分组次数，不修改服务数据。在 `Options.cs` 增加默认空的 `DiagnosticStoreRoot` 测试参数；空值从程序集 `Bin` 目录的上一级定位 `Store/Diagnostics`，非空值只用于显式启动的隔离实例。在 `Publish-win-x64.ps1` 将统计脚本复制到发布包的 `Tools/` 并检查其存在，保留发布根 `Store` 不进入 `Remove-PublishOutputs` 的清理集合；`Store/Diagnostics` 是运行数据，不纳入发布源文件。更新现有部署说明，写明 HTTPS 反向代理、覆盖 `X-Real-IP`、31002 只允许代理访问及客户端正式地址检查；不自动修改防火墙或代理配置。

## 实施偏差处理

- **直接修复**：仅在已确认设计、可观察行为和验收不变，修改仍在允许范围，不增加依赖，不改变公开接口、协议、数据格式或职责，不引入无关重构，并能用计划验证证明时，自行做最小编译、兼容或接线修复；实施结果记录症状、证据、实际文件、修复、与计划差异、验证及剩余风险。
- **先询问用户**：上述任一直接修复条件不能确定，多个合理修法会改变可观察行为，或需要修改未列但直接相关文件且未明显扩大总体范围时，暂停受影响工作，取得明确授权后记为“用户批准的实施偏差”。
- **停止并报告**：需要改变架构、公开接口、协议、数据格式、依赖或已确认设计；允许范围明显扩大、需增加新功能；实际项目与计划根本冲突、可靠实现仍需计划外研究或技术决策；或用户要求停止重设计时，停止受影响事项等待修订计划。新增目标视为新需求，不作为默认偏差。
