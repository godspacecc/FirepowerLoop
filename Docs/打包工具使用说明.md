# 打包工具使用说明

逐项整理，当前介绍前三项及本轮确认的两平台快速打包。按 2026-10-30 当前代码核对；本文说明工具行为，不代表已经实际打包验收。第二、三项、完整包新增的基线/准备记录，以及两平台快速打包改动仍待 Unity 验证，详见各节说明。

## 第一项：PC → 完整打包

菜单：`Tools → 打包 → PC → 完整打包`

**用途：把当前代码和资源重新做成一套完整的 Windows 游戏、安装器，并同步到本地资源服发布目录。**

### 什么情况下用

| 实际情况 | 为什么选它 |
| --- | --- |
| 第一次给这个项目出 PC 包，没有可复用的打包结果 | 它会重新生成所需代码和资源，不要求先有最近 Host 结果或 AOT 基线。 |
| 改了底层代码、插件、程序集或影响代码编译的设置 | 旧的底层代码结果可能已不适用，需要重新生成。 |
| 准备正式交付一份包含最新代码、最新资源的完整游戏 | 重新生成各阶段产物并检查一致性，避免把临时验证时复用的旧结果带进交付包。仍需另外验收实际运行。 |
| 不清楚上次打包之后改了什么，也无法确认旧结果能否复用 | 选择完整流程，减少依赖人工判断旧结果是否适用。 |

**它的价值是重新生成完整的一套结果。** 如果游戏本体已经成功，只是安装器或发布失败，不必因此再跑一遍完整打包，见后面的补做表。

### 点下去后，按什么顺序做

以下路径都从仓库根目录 `E:/GitHub/FirepowerLoop/` 开始。`<游戏批次>`、`<安装器批次>`、`<资源版本>`是运行时生成的名称，不是同一个编号；以本次日志显示的路径为准。

1. **检查打包条件。** 必要时切换 Windows 平台并等待 Unity 重载；检查项目设置和安装器编译器。缺少 Inno Setup 6 的 `ISCC.exe` 时会要求选择，未配置成功就停止。

   **文件位置：**项目设置在 `Client/ProjectSettings/`。安装器编译器使用本机已记录的位置，或尝试 `%LOCALAPPDATA%/Programs/Inno Setup 6/ISCC.exe`，找不到再由你选择。这一步不生成游戏文件，检查结果在 Unity Console。

2. **重新生成代码。** 编译游戏逻辑，生成底层代码所需的 AOT 和桥接资料。把本次编译好的游戏代码放入待打包目录，确保后面打进去的是最新代码。同名资源保留原来的标识，不因覆盖内容变成另一份资源。

   **文件位置：**游戏 DLL 先生成到 `Client/HybridCLRData/HotUpdateDlls/StandaloneWindows64/`，AOT DLL 生成到 `Client/HybridCLRData/AssembliesPostIl2CppStrip/StandaloneWindows64/`；随后复制到 `Client/Assets/Game/Dlls/`，成为 `Game.dll.bytes`、各 AOT 的 `.dll.bytes` 和 `HybridCLRAssemblyList.bytes`。辅助生成文件在 `Client/Assets/HybridCLRGenerate/`；当前 Windows 编辑器使用的桥接 C++ 文件在 `Client/HybridCLRData/LocalIl2CppData-WindowsEditor/il2cpp/libil2cpp/hybridclr/generated/`。这些是制作中间文件，尚不是可运行游戏。

3. **重新构建完整游戏资源。** 生成新的资源版本，并把完整资源放入待打包的内置目录。

   **文件位置：**从项目收集资源（包括上一步的 `Client/Assets/Game/Dlls/`），输出到 `Client/Bundles/StandaloneWindows64/DefaultPackage/<资源版本>/`，同时将完整内置资源写入 `Client/Assets/StreamingAssets/yoo/DefaultPackage/`。后者会在生成游戏时被带进游戏目录。

4. **检查这些资源是否齐全。** 检查版本、资源清单、游戏实际读取的二进制资源目录，以及清单要求的每个资源文件；记录本次文件内容，用于下一步核对。

   **文件位置：**先检查上一步 `Client/Bundles/StandaloneWindows64/DefaultPackage/<资源版本>/` 的输出，再逐文件检查 `Client/Assets/StreamingAssets/yoo/DefaultPackage/`。包含 `DefaultPackage.version`、对应版本的 `.bytes` / `.hash` 清单、`BuildinCatalog.bytes` / `.json` 和全部所需资源包。最终游戏的资源对比保存在内存；新增的快速补做准备记录保存到 `Client/Build/PcPrepared/<准备批次>/prepared.json`，`Client/Build/PcPrepared/latest.json` 指向最新准备批次。最终游戏生成失败时仍可读取这份记录，详见第五项。失败原因在 Unity Console。

5. **生成 Windows 游戏并核对实际输出。** 生成 `FirepowerLoop.exe` 及配套文件，分离调试资料；再检查导出的游戏目录里的资源是否与本次记录一致。缺文件、版本错误或内容不一致都会停止，不能继续做安装器。

   **文件位置：**游戏输出到 `Client/Build/Windows/<游戏批次>/FirepowerLoop/`，启动文件是其中的 `FirepowerLoop.exe`；实际核对的内置资源在该目录的 `FirepowerLoop_Data/StreamingAssets/yoo/DefaultPackage/`。调试资料单独放到 `Client/Build/Windows/<游戏批次>/Symbols/`。通过检查后，成功记录写入 `Client/Library/FirepowerLoopBuild/BuildState.json`。

   **这份记录用来做什么：**让后续工具知道“上次成功生成了什么、文件在哪里”。本次完整打包会记录游戏、资源和 AOT 路径、版本，并保存热更新基线位置，后续热更新入口据此找到配套游戏；同一文件还保存由 Host 流程写入的最近 Host 记录，本次完整打包不更新它。两种PC快速打包改为读取第4步独立的准备记录，才能在尚无成功游戏、只有准备阶段成功时补做，不能把Host成功记录当成完整的出包准备记录。

   **它不是什么：**它只保存记录，不保存游戏文件本身；即使记录还在，实际文件被删除或不符合校验要求，也不能直接复用。它不能让失败流程自动断点续跑，玩家运行游戏也不需要它。此处写入成功记录只表示游戏本体已通过检查，不表示后面的安装器和发布已经成功。

   **新增的热更新基线（待验证）：**同批次的 `Client/Build/Windows/<游戏批次>/HostBaseline/` 保存独立 AOT、运行清单、原始 `Game.dll` 以及宿主输入和实际游戏文件指纹；其位置记入上述状态文件。第三项热更新使用它核对已有游戏及其支持的代码需求，不再把可能被后续构建覆盖的生成目录当成可靠基线。它是开发侧资料，不放进安装器。

6. **生成安装器。** 用刚才通过检查的游戏目录制作安装器，再检查安装器身份和文件内容。

   **文件位置：**读取第 5 步的完整 `FirepowerLoop/` 游戏目录，输出到 `Release/WindowsInstaller/Installer_<安装器批次>/`。其中的 `FirepowerLoop-Setup-<发布序号>.exe` 是安装器，`app-update-windows.json` 是更新描述。安装器生成失败时，日志会列出保留的游戏路径和未完成安装器目录。

7. **发布到本地资源服目录。** 同步同版本资源，再放入安装器和更新描述。完成后才报告“完整打包完成”。这里的发布是准备本地发布目录，不等于上传公网服务器或提交商店。

   **文件位置：**目标是 `Release/ResourceServer/ResourceServerBundle_<批次>/`；已有可用发布包时会更新该发布包，不保证每次新建目录。第 3 步生成的同版本资源同步到其中的 `ResourceFiles/`；第 6 步的安装器和 `app-update-windows.json` 发布到其中的 `AppUpdates/Windows/`。发布失败时保留第 5、6 步的原始产物，按日志指向的本次目录补做。

8. **询问是否启动资源服。** 可以启动本机资源服进行测试；不启动不会撤销已经生成、发布好的文件。

   **文件位置：**服务使用第 7 步发布包里的 `ResourceFiles/`，并提供同发布包内的安装器更新内容。这一步不重新生成游戏或安装器；本机服务状态记录在 `Client/Library/FirepowerLoopBuild/LocalResourceServer.json`，启动结果和访问地址显示在 Unity Console。

本入口不复用旧 AOT、旧游戏 DLL 或最近 Host 结果。已删除多余的预备游戏构建，但生成 AOT 所需的内部构建仍会执行，因此不能理解成“整个流程只编译一次”。

### 最后会得到什么

以下路径相对于仓库根目录，具体批次以完成提示和日志为准。

| 产物 | 位置与用途 |
| --- | --- |
| 可运行的游戏目录 | `Client/Build/Windows/<时间批次>/FirepowerLoop/`。包含 EXE 及配套文件，不能只拷贝一个 EXE。 |
| 调试资料 | 同批次的 `Symbols/`。保留用于排查问题，不作为玩家游戏目录发出。 |
| 安装器 | `Release/WindowsInstaller/Installer_<批次>/`。供玩家安装游戏。 |
| 本地资源服发布包 | `Release/ResourceServer/` 下相应发布目录，包含资源、安装器及更新描述。 |

游戏包含完整内置资源，不是首次启动必须下载全部资源的小启动包；但“完整内置”也不等于关闭联网和更新功能。

### 失败后怎么处理，哪些不用重做

先看日志中的失败阶段，不要仅凭“失败”两个字重新出整包。

| 失败位置 | 这时有什么 | 应该怎么做 |
| --- | --- | --- |
| 环境检查、代码生成、资源构建或游戏检查 | 尚无本次通过全部检查的游戏 | 修复具体错误，再执行完整打包；不要把残留输出当成成功包。 |
| 游戏已通过检查，安装器生成失败 | 游戏目录已保留 | 修复安装器问题，使用 `Tools → 打包 → PC → 快速打包 → 生成安装器`，选择这次保留的 EXE。这个辅助入口只生成安装器，不会自动发布。 |
| 安装器已生成，资源同步或安装器发布失败 | 游戏和安装器都已保留 | 核对并同步同版本资源，再补发布现有安装器；不用重新生成游戏或安装器。目前安装器补发布需要使用已有脚本或代码入口，没有独立的一键菜单，可交给开发协助处理。 |
| 发布成功后，本机资源服启动失败 | 游戏、安装器和本地发布文件已经完成 | 排查端口占用或服务器启动错误，再用 `Tools → 服务器 → PC → 启动资源服`。不用重新打包。 |

如果补做期间又修改了游戏代码或资源，应重新判断是否需要生成新游戏；“补做”指继续交付原来那一批结果，不会自动带入后续修改。

### 怎样判断完成到哪一步

- **Player 构建成功**：游戏目录已通过检查，安装器和发布还没完成。
- **安装器生成成功（尚未发布）**：安装器已经做好，资源服发布还没完成。
- **完整打包完成**：游戏、安装器以及本地发布步骤都已完成；实际安装、启动和游玩仍需验收。

源码核对：[完整流程](../Client/Assets/Editor/Build/BuildUtility.cs)、[最终游戏资源校验](../Client/Assets/Editor/Build/PcBuiltinResourceValidator.cs)、[安装器生成与发布](../Client/Assets/Editor/Build/WindowsInstallerPublishUtility.cs)、[已有游戏补做安装器菜单](../Client/Assets/Editor/Build/WindowsInstallerMenu.cs)。

## 第二项：PC → 启动包（首次下载资源）

菜单：`Tools → 打包 → PC → 启动包（首次下载资源）`，原名“首包完整打包”。

**当前状态：**改名、去掉额外预备构建、加强产物校验已写入代码；按用户要求暂不测试，尚未完成本轮 Unity 编译与测试验证。以下介绍当前代码准备执行的流程，不代表已实测出包成功。

**用途：生成一个不携带完整游戏资源的 Windows 安装包，让玩家安装后首次启动时再下载资源。** 它不是“第一次给项目打包必须使用”的入口，也不是快速打包。

### 什么情况下用

| 实际情况 | 为什么选它，而不是完整打包 |
| --- | --- |
| 希望先分发较小的安装器，再让玩家启动后下载游戏资源 | 完整打包把资源放进安装器；本工具把资源留在资源服，安装器主要提供启动程序及资源清单。实际节省多少体积需出包测量。 |
| 要测试新玩家从没有资源缓存到下载完成、进入游戏的过程 | 完整包自带资源，不能直接代替“必须下载资源才能进入”的测试。测试时还需使用没有旧缓存的环境。 |
| 要验证下载失败、断网、重新启动后的恢复表现 | 启动包提供真正依赖下载的测试条件；本工具本身不会自动完成这些测试。 |

如果只是想把完整游戏直接交给别人安装运行，优先选第一项。启动包在**没有网络、也没有可用缓存**时不能进入游戏；本机资源服启动成功，也不等于其他玩家已经能通过公网访问它。

### 点下去后，按什么顺序做

以下路径相对于仓库根目录 `E:/GitHub/FirepowerLoop/`。各批次、资源版本与发布序号以本次日志为准。

1. **检查打包条件。** 必要时切换 Windows 平台并等待重载，检查项目设置和安装器编译器；条件不足就停止。

   **文件位置：**项目设置在 `Client/ProjectSettings/`。编译器使用本机记录的 `ISCC.exe`，或尝试 `%LOCALAPPDATA%/Programs/Inno Setup 6/ISCC.exe`，找不到时要求选择。这一步不生成游戏文件，结果显示在 Unity Console。

2. **重新生成代码，放入待打包目录。** 重新编译游戏逻辑，生成 AOT 和桥接资料；不复用旧代码结果。已去掉额外预备游戏构建，生成 AOT 所需的内部构建仍保留。

   **文件位置：**游戏 DLL 生成到 `Client/HybridCLRData/HotUpdateDlls/StandaloneWindows64/`，AOT DLL 生成到 `Client/HybridCLRData/AssembliesPostIl2CppStrip/StandaloneWindows64/`，随后复制到 `Client/Assets/Game/Dlls/` 供资源构建读取。辅助生成文件在 `Client/Assets/HybridCLRGenerate/`；当前 Windows 编辑器的桥接 C++ 文件在 `Client/HybridCLRData/LocalIl2CppData-WindowsEditor/il2cpp/libil2cpp/hybridclr/generated/`。

3. **构建完整下载资源，只把清单放进启动包。** 资源仍然需要全部构建；减少的是安装包携带的资源，不是省略资源构建。

   **文件位置：**完整资源输出到 `Client/Bundles/StandaloneWindows64/DefaultPackage/<资源版本>/`。待打包目录 `Client/Assets/StreamingAssets/yoo/DefaultPackage/` 只放版本、资源清单和空的内置资源目录，不放游戏资源包。这一步会清理并重写该内置目录，不能把它当作上一次完整包资源的备份。

4. **核对启动清单和下载资源是否配套。** 检查完整资源是否缺包或损坏；检查启动包的版本和清单是否与它一致，二进制内置目录能否读取、是否为空，并拒绝误放进去的资源包。

   **文件位置：**同时读取第 3 步的 `Client/Bundles/StandaloneWindows64/DefaultPackage/<资源版本>/` 与 `Client/Assets/StreamingAssets/yoo/DefaultPackage/`。记录文件内容供后续对比；这份对比记录只在内存里，不生成快照文件。失败原因显示在 Unity Console。

5. **生成 Windows 启动包，检查真正导出的文件。** 生成 EXE 和配套文件，检查实际游戏目录里是否只有正确清单、没有误带资源；同时复查完整下载资源在这期间没有改变。任一检查失败，就停止后续安装器流程。

   **文件位置：**游戏输出到 `Client/Build/Windows/<游戏批次>/FirepowerLoop/`，其中 `FirepowerLoop.exe` 是启动文件。实际检查该目录下的 `FirepowerLoop_Data/StreamingAssets/yoo/DefaultPackage/`。调试资料分离到同批次的 `Symbols/`，不随玩家目录交付。

6. **保存成功记录，供后续工具查找。** 记录这次游戏、资源、AOT 和 Host 结果的路径、版本及相关校验信息，热更新入口据此找到配套游戏。两种PC快速入口使用另行保存的准备记录；它在最终游戏生成前就保存，因此游戏生成失败也能补做。

   **文件位置：**写入 `Client/Library/FirepowerLoopBuild/BuildState.json`。它只保存记录，不保存游戏文件；实际文件丢失或不符合校验要求，记录不能替代它们。它不负责失败流程自动续跑，也不表示安装器与发布已经成功，玩家运行游戏不需要它。

   **用于热更新的独立基线（待验证）：**同时在 `Client/Build/Windows/<游戏批次>/HostBaseline/` 保存这次宿主对应的 AOT 副本、运行清单、原始 `Game.dll` 和输入/游戏指纹，状态文件记录其位置。第三项通过它确认“这些更新仍针对这份旧游戏”，热更新不覆盖这份基线。资料不放入安装器。

7. **生成安装器，并发布同版本资源。** 使用已通过检查的启动包制作安装器，检查安装器文件，再同步完整下载资源及安装器更新描述。

   **文件位置：**读取第 5 步的完整 `FirepowerLoop/` 目录，安装器输出到 `Release/WindowsInstaller/Installer_<安装器批次>/`，包括 `FirepowerLoop-Setup-<发布序号>.exe` 和 `app-update-windows.json`。本地发布目标为 `Release/ResourceServer/ResourceServerBundle_<批次>/`：完整下载资源放在 `ResourceFiles/`，安装器和更新描述放在 `AppUpdates/Windows/`。有可用发布包时会更新已有目录，不保证每次新建。这里不包含上传公网服务器或提交商店。

8. **自动启动本机资源服。** 本入口发布完成后会直接尝试启动同版本资源服，供启动包下载资源；与第一项完成后询问是否启动不同。

   **文件位置：**服务使用第 7 步发布目录里的 `ResourceFiles/` 及安装器更新文件。本机服务状态写入 `Client/Library/FirepowerLoopBuild/LocalResourceServer.json`，启动结果和访问地址显示在 Unity Console；不重新生成游戏或安装器。上述说明针对手动菜单入口，CI 流程会在生成安装器和记录产物后返回，不自动发布或启动服务。

### 最后会得到什么

| 产物 | 位置与用途 |
| --- | --- |
| Windows 启动包游戏目录 | `Client/Build/Windows/<游戏批次>/FirepowerLoop/`。能启动程序，但没有缓存时需要下载资源才能进入游戏；不能只发一个 EXE。 |
| 安装器 | `Release/WindowsInstaller/Installer_<安装器批次>/`。安装上述启动包，不包含完整游戏资源包。 |
| 配套完整下载资源 | `Client/Bundles/StandaloneWindows64/DefaultPackage/<资源版本>/`，发布后位于资源服发布包的 `ResourceFiles/`。必须与启动清单配套。 |
| 本地资源服发布包 | `Release/ResourceServer/ResourceServerBundle_<批次>/`，包含下载资源、安装器和更新描述。 |
| 调试资料与复用记录 | 同游戏批次的 `Symbols/` 以及 `Client/Library/FirepowerLoopBuild/BuildState.json`，用于开发排查和后续工具，不作为玩家游戏文件分发。 |

### 失败后怎么处理，哪些不用重做

| 实际情况 | 处理方式与文件位置 |
| --- | --- |
| 代码、资源构建或启动包检查失败 | 按 Console 中的失败阶段修复后重跑本入口。第 3、5 步目录里的残留文件不能当作通过检查的交付包。 |
| 启动包通过检查，但安装器生成失败 | 保留第 5 步的游戏目录。使用 `Tools → 打包 → PC → 快速打包 → 生成安装器`，选择其中的 EXE 补做；该辅助入口只生成安装器，不自动发布。 |
| 安装器已生成，但发布失败 | 保留 `Release/WindowsInstaller/Installer_<安装器批次>/` 的安装器及第 3 步同版本资源。修复同步问题后补发布，无需重建游戏或安装器；安装器补发布目前需使用已有脚本或代码入口，可交给开发协助处理。 |
| 发布完成，但本机资源服启动失败 | 第 7 步产物仍在。排查端口或启动错误，再用 `Tools → 服务器 → PC → 启动资源服`；不用重打包。 |
| 安装后下载失败或无法进入游戏 | 先核对游戏配置的资源服地址、网络可达性，以及发布包 `ResourceFiles/` 是否为配套版本；不要先把它判断成需要重新打包。若确实改了程序或内置配置，再重新判断是否需要出新启动包。 |

补做指继续交付原来那一批结果，不会自动带入后续代码或资源改动。看到“PC 首包完成”表示游戏、安装器及本地发布步骤完成；随后仍可能出现资源服启动失败。实际安装、首次下载和进入游戏需要另行验收。

## 第三项：PC → 构建热更新（代码+资源）

菜单：`Tools → 打包 → PC → 构建热更新（代码+资源）`，原名“Host代码+资源更新”。

**当前状态：**本项流程与宿主基线保存已写入代码，尚未完成 Unity 编译/测试验证。用户要求暂不测试仍生效。以下说明待验证实现的行为，不代表已在旧游戏中验证更新成功。

**用途：给已有游戏提供可下载的玩法代码和资源更新，不重新生成游戏 EXE 或安装器。** 这里的 Host 指已经安装、负责启动和加载更新的游戏程序。

### 什么情况下用

| 实际情况 | 选择依据 |
| --- | --- |
| 已有可运行的游戏，只调整玩法代码、数值配置、界面或关卡资源 | 若修改仍兼容已有程序，可通过本工具生成更新内容，不要求玩家重新安装。数值配置仍须先按项目规范生成。 |
| 需要反复测试“旧游戏下载新玩法后进入游戏” | 本工具构建下载资源并启动本地资源服；已有游戏必须配置到这个服务，且使用与基线对应的程序。 |
| 改了启动程序、底层运行代码、插件或构建设置 | 改用完整包或启动包。热更新无法把这些变化替换进已经安装的原生游戏程序。 |
| 没有可信的宿主基线，只有以前留下的DLL文件 | 先重新生成完整包或启动包。旧目录存在不代表与测试端的游戏匹配，工具会拒绝直接复用。 |

本入口不生成新的安装器，也不自动同步 `Release/ResourceServer/`。其用途是构建并本地测试热更新；需要对外发布时，还要另外发布配套资源。

### 点下去后，按什么顺序做

路径相对于仓库根目录 `E:/GitHub/FirepowerLoop/`，批次及资源版本以日志为准。

1. **找到已有游戏和它的独立基线。** 读取最近记录的游戏及基线位置；基线缺失、被改坏或不属于该游戏时停止，并提示重新生成完整包或启动包。

   **文件位置：**读取 `Client/Library/FirepowerLoopBuild/BuildState.json`。正常手动打包的游戏在 `Client/Build/Windows/<原游戏批次>/FirepowerLoop/`，基线在同批次的 `HostBaseline/`。其中 `baseline.json` 记录身份指纹，`Aot/` 保存独立AOT副本，`HybridCLRAssemblyList.bytes` 保存运行清单，`Game.dll` 保存原始代码以比较外部调用需求。CI恢复的归档可能位于独立恢复目录，以状态记录为准。本步不新建游戏文件。

2. **检查这次修改是否仍适合旧游戏。** 核对基线与实际游戏程序，比较宿主输入。检查覆盖 Boot、非Game运行源码、程序集定义、原生依赖、内置资源、启动场景依赖、项目及包设置等；发现变化就拒绝只做热更新。普通Game玩法源码和远程资源允许变化，最终兼容性仍需实际游戏验收。

   **文件位置：**读取 `Client/Assets/Boot/`、`Client/Assets/Game/Scenes/Boot.unity` 及其依赖、`Client/ProjectSettings/`、`Client/Packages/` 等实际输入，同时核对第1步游戏目录中的 EXE、`UnityPlayer.dll`、`GameAssembly.dll` 和 `FirepowerLoop_Data/StreamingAssets/windows-release.json`。本步不重写基线，失败原因在 Unity Console。检查采取保守策略，某些设置变化也可能要求重新出包。

3. **只编译可热更新代码，检查需求后复制原宿主对应的AOT。** 编译新的Game DLL，比较它与原始Game使用的外部类型、成员及具体泛型调用。出现此前未使用的外部需求时，无法确定旧游戏是否已保留相应代码，因此要求重新出完整包或启动包。Game包含原生调用或回调时采用更保守规则：只要该DLL内容变化，就要求重出程序，避免缺少原生桥接。AOT从独立基线读取，不重新裁剪或生成，不把新AOT冒充旧游戏的基线。

   **文件位置：**新Game DLL生成到 `Client/HybridCLRData/HotUpdateDlls/StandaloneWindows64/`。它和第1步 `HostBaseline/Aot/` 的AOT副本一起复制到 `Client/Assets/Game/Dlls/`，形成待资源打包的 `.bytes` 文件。原 `HostBaseline/` 保持不变。

4. **构建完整下载资源，保持工程内置包不变。** 将最新玩法代码和资源做成新的远程资源版本；并对比内置目录构建前后内容，避免误改前两项准备的内置资源。

   **文件位置：**新资源输出到 `Client/Bundles/StandaloneWindows64/DefaultPackage/<新资源版本>/`；对比但不改写 `Client/Assets/StreamingAssets/yoo/DefaultPackage/`。内置目录对比记录只在内存中，不产生快照文件。

5. **逐包校验，并再次检查宿主没有变化。** 检查清单要求的每个下载资源文件是否存在、长度与内容是否正确，再核对原游戏、AOT基线及底层输入。构建期间输入发生变化也会停止，不启动资源服。

   **文件位置：**读取第4步新资源目录、第1步原游戏及基线目录、第2步宿主输入。资源内容对比记录保存在内存，错误显示在 Unity Console；不新增安装包文件。

6. **记录这次热更新结果。** 更新最近Host结果和最近资源版本，供后续查询及归档。它表示资源构建已通过检查，不表示本机服务已成功启动。热更新不生成新的快速打包准备记录；需要把新玩法做成完整包或启动包时，选“复用 AOT 打包”重新准备代码和资源，或执行完整流程。

   **文件位置：**写入 `Client/Library/FirepowerLoopBuild/BuildState.json` 中的Host和资源记录。已有游戏记录、独立基线位置以及AOT基线记录不被本次热更新替换；实际下载资源仍保存在第4步的目录。

7. **直接从新资源目录启动本机资源服。** 成功后输出版本、目录和访问地址，供已有游戏下载测试。CI路径记录产物后返回，不自动启动本地服务。

   **文件位置：**服务直接读取 `Client/Bundles/StandaloneWindows64/DefaultPackage/<新资源版本>/`；本机服务状态保存在 `Client/Library/FirepowerLoopBuild/LocalResourceServer.json`。不会把这批资源自动复制进 `Release/ResourceServer/`，不会生成或发布安装器。启动结果显示在 Unity Console。

### 最后会得到什么

得到一份新版本的完整下载资源，以及记录其位置的Host成功记录；手动菜单还会尝试启动本机资源服。不会得到新的 `FirepowerLoop.exe`、`Symbols/` 或安装器，原游戏与独立AOT基线保持不变。资源目录包含该版本所需的完整资源文件，不应把“热更新”理解成输出目录里只有变化的文件。

### 失败后怎么处理，哪些不用重做

| 实际情况 | 处理方式与位置 |
| --- | --- |
| 提示基线缺失、损坏或宿主输入变化 | 重新生成完整包或启动包，得到新的游戏和同批次 `HostBaseline/`，并让测试端使用新游戏。不要手工修改 `baseline.json` 来绕过检查。 |
| Game编译或资源校验失败 | 修复Console指向的错误后重跑本项。只有确认涉及底层程序时才改用完整打包，不必每次都重出安装器。 |
| 资源构建成功，但本机资源服启动失败 | 新资源仍在第4步输出目录。修复服务问题后，可由开发直接对该目录补启动；或者先将该版本发布/更新到本地发布包，再启动其资源服。不要直接假定普通“启动资源服”菜单一定选择这次Bundles目录，它也会检查已有Release发布包。无需为端口问题重出游戏。 |
| 本机更新正常，但其他人仍拿到旧资源 | 核对对方游戏配置的服务地址和实际发布目录。本工具只启动本机服务，不等于远端服务器已更新。 |

旧游戏能否使用本次更新，应在该游戏中实际下载并运行确认；反射等动态依赖不等于静态引用检查已经覆盖。工具不会自动把玩家电脑上安装的程序与本机基线配对，也不会代替运行验收。

源码核对：[热更新流程](../Client/Assets/Editor/Build/BuildUtility.cs)、[PC宿主基线与输入检查](../Client/Assets/Editor/Build/PcHotUpdateBaseline.cs)、[完整下载资源校验](../Client/Assets/Editor/Build/PcBuiltinResourceValidator.cs)、[基线归档恢复](../Client/Assets/Editor/Build/HostBaselineArchive.cs)。

## 第四项：PC / Android → 快速打包 → 复用 AOT 打包

两平台各保留两个快速入口。本项适合日常改完玩法代码、配置或资源后，重新出测试安装包；它会重新编译玩法代码、重新打资源，只复用底层 AOT 及对应的桥接资料。原“复用代码打包”菜单已取消。

**当前状态：**以下对应已写入的待验证代码；尚未执行 Unity 编译、测试或真实打包。

### 什么情况下用

| 实际情况 | 选择 |
| --- | --- |
| 改了普通玩法、数值、图片或界面资源，需要新的测试包 | 选本项；如果检查发现不兼容，按提示改用完整包或启动包。配置修改仍须先按项目规范生成。 |
| 改了 Boot、底层插件、程序集布局或构建设置 | 使用完整包或启动包，重新准备底层资料。 |
| 新玩法增加旧底层未保留的外部调用、泛型或原生回调需求 | 本项会保守拒绝；重新完整准备，不会自动偷偷执行完整生成。 |
| 代码和资源都已经准备好，只是最后生成游戏程序失败 | 用第五项“复用全部打包”，不必重复编玩法和打资源。 |
| 准备正式交付 | 优先完整流程，并完成实际运行验收；快速包主要服务日常验证和补做。 |

**包型沿用最近可信准备批次：**之前准备的是完整包，本次仍内置完整资源；之前准备的是启动包，本次仍只内置清单、首次运行下载资源。两个入口不会因为叫“快速”而把完整包自动变成启动包。Android这里沿用普通测试包设置，不沿用渠道候选包的正式签名流程。

### 点下去后，按什么顺序做

路径均相对于仓库根目录；`<平台>`为PC的 `StandaloneWindows64` 或Android的 `Android`。

1. **读取本平台的准备记录，检查底层还能否复用。** 检查包型、平台、版本、不可变副本、底层源码/设置和桥接资料；缺记录、记录损坏或不匹配时停止，提示重新完整准备。

   **文件位置：**PC读取 `Client/Build/PcPrepared/latest.json` 和对应 `<准备批次>/prepared.json`、`Aot/`、`Game.dll`、`HybridCLRAssemblyList.bytes`。Android读取 `Client/Library/FirepowerLoopBuild/AndroidQuickInputs.json`、`AndroidQuickAot/<原资源版本>.json` 和同版本目录内的AOT DLL、`baseline-game.bytes`、`runtime-list.bytes`。检查 `Client/ProjectSettings/`、`Client/Packages/`、Boot及实际底层依赖，生成资料位于 `Client/Assets/HybridCLRGenerate/` 与本机HybridCLR的 `generated/` 目录。

2. **重新编译玩法代码，核对它能使用原底层资料。** 新增无法证明兼容的需求时停止；通过后复制新玩法代码和冻结的AOT，供这次资源构建使用。

   **文件位置：**新玩法代码在 `Client/HybridCLRData/HotUpdateDlls/<平台>/Game.dll`；与第1步的独立AOT一起放入 `Client/Assets/Game/Dlls/`。不会重新生成裁剪AOT或原生桥接。

3. **重新打资源，保存下一次可补做的准备记录。** 生成新资源版本；按原包型准备完整内置资源或仅启动清单，逐包核对远端资源及内置内容。还会比较编译前后的源码、资源和设置，避免构建中途改动后登记错误结果。

   **文件位置：**新资源在 `Client/Bundles/<平台>/DefaultPackage/<新资源版本>/`，内置内容在 `Client/Assets/StreamingAssets/yoo/DefaultPackage/`；新准备记录沿用第1步各平台的位置，独立副本写入新批次。它在最终程序开始生成前就落盘，因此后一步失败仍可补做。

4. **生成新的游戏程序，检查实际装入的资源。** PC检查导出目录，Android读取实际APK里的资源并比对；构建结束后再次核对输入没有变化。验证失败时不发布安装包。

   **文件位置：**PC游戏在 `Client/Build/Windows/<新游戏批次>/FirepowerLoop/`，调试资料在同批次 `Symbols/`；核对游戏内 `FirepowerLoop_Data/StreamingAssets/yoo/DefaultPackage/`。Android输出在 `Client/Build/Android/<新游戏批次>/FirepowerLoop-<应用版本>.apk`，读取APK的 `assets/yoo/DefaultPackage/`。APK应用版本递增，资源版本使用第3步版本。

5. **保存游戏成功记录，再制作/发布安装包。** PC为新游戏保存后续热更新依据，然后生成Windows安装器；Android保存新APK记录并发布APK。发布使用本次明确资源版本，不扫描选择另一批较新资源。

   **文件位置：**成功记录在 `Client/Library/FirepowerLoopBuild/BuildState.json`。PC热更新依据在本次 `Client/Build/Windows/<新游戏批次>/HostBaseline/`，安装器在 `Release/WindowsInstaller/Installer_<安装器批次>/`，资源与安装更新在 `Release/ResourceServer/ResourceServerBundle_<发布批次>/`。Android资源和APK更新在 `Release/ResourceServer/Android/ResourceServerBundle_<发布批次>/`，APK置于其中 `AppUpdates/Android/`。发布成功后可按提示启动本机资源服，不等于已部署到公网。

### 失败后怎么处理

- 玩法编译或资源准备失败：修复后重跑本项；若涉及底层或兼容性门禁，重新完整准备。
- 准备记录已保存，最后生成游戏失败：修复构建环境后，用第五项补做。若修复需要修改代码、资源或设置，旧记录可能失效，应按提示重新准备。
- 游戏已通过校验，只是PC安装器或两平台发布失败：保留第4步的游戏以及第3步资源，补做安装器/发布即可，不必再生成游戏。

源码核对：[PC流程](../Client/Assets/Editor/Build/BuildUtility.cs)、[PC准备记录](../Client/Assets/Editor/Build/PcQuickBuildUtility.cs)、[Android流程](../Client/Assets/Editor/Build/AndroidBuildUtility.cs)、[Android AOT检查](../Client/Assets/Editor/Build/AndroidQuickAotUtility.cs)。

## 第五项：PC / Android → 快速打包 → 复用全部打包

**用途：代码和资源已经准备好，只补做最终游戏程序及后续交付。** 典型情况是最后生成Windows游戏或APK失败，修好环境后重试。也可用于没有内容改动时重新出同一批内容的安装包。

**当前状态：**同第四项，代码待Unity验证。此项不会重新编译玩法DLL、重新生成AOT或重打资源；Unity生成最终程序时仍可能编译原生代码，不能理解成完全没有编译过程。

### 点下去后，按什么顺序做

1. **找到准备记录，并确认代码、资源及设置仍与该批次一致。** 本项比第四项更严格：普通玩法或美术资源变化也会使它拒绝执行，避免让你以为新修改已进入安装包。没有可信记录时，不用时间戳或仅看文件存在来猜测可复用性。

   **文件位置：**PC读取 `Client/Build/PcPrepared/latest.json` 与对应准备目录；Android读取 `Client/Library/FirepowerLoopBuild/AndroidQuickInputs.json` 与 `AndroidQuickAot/<资源版本>.json`、同版本独立副本。同时检查项目源码/资源、配置、生成资料、`Client/Assets/Game/Dlls/`、`Client/Assets/StreamingAssets/yoo/DefaultPackage/` 和记录中的 `Client/Bundles/<平台>/DefaultPackage/<资源版本>/`。本步不重新生成这些文件。

2. **沿用资源版本和完整/启动包类型，生成新的游戏程序。** 不创建新的资源版本；最终程序生成到新游戏批次，不覆盖之前的游戏。Android会正常分配新的应用版本和版本码，它们与资源版本是两件事。

   **文件位置：**PC输出 `Client/Build/Windows/<新游戏批次>/FirepowerLoop/` 及同批次 `Symbols/`；Android输出 `Client/Build/Android/<新游戏批次>/FirepowerLoop-<应用版本>.apk`。原资源仍在第1步的版本目录。

3. **核对实际输出，并记录这次成功游戏。** 检查实际Player/APK内置资源，以及准备输入在构建中是否变化。PC还保存新游戏对应的热更新依据。

   **文件位置：**PC核对 `FirepowerLoop_Data/StreamingAssets/yoo/DefaultPackage/`；Android核对APK内 `assets/yoo/DefaultPackage/`。成功记录写入 `Client/Library/FirepowerLoopBuild/BuildState.json`，PC新依据在同游戏批次 `HostBaseline/`。这一步成功不代表安装器或发布已成功。

4. **完成安装器与发布。** PC生成新安装器，Android发布新APK；同步的资源仍是第1步明确版本。发布后再次检查目标资源，防止发布了错误或不完整的包。

   **文件位置：**PC安装器在 `Release/WindowsInstaller/Installer_<安装器批次>/`，发布在 `Release/ResourceServer/ResourceServerBundle_<发布批次>/`；Android发布在 `Release/ResourceServer/Android/ResourceServerBundle_<发布批次>/`，APK在其中 `AppUpdates/Android/`。安装包生成成功但发布失败时，这些已生成产物保留用于补发布。

### 记录到底有什么用

准备记录证明“本次代码和资源已准备到哪一步、哪些文件属于同一批”；同时保存必要的独立AOT/代码参照，检查内容是否变化。它不是完整备份：如果资源目录、待打包DLL或内置目录被其他构建改写，不会自动恢复所有文件。此时按提示重新准备，不手工改JSON来绕过检查。删除 `Client/Library/` 会丢失Android准备记录；PC记录位于 `Client/Build/PcPrepared/`，删除该目录也会失去快速复用依据。

成功游戏记录则证明“最终程序也已经通过检查”，主要供后续热更新、交付和查找产物使用。两类记录分别保存，才能区分“还要生成游戏”与“只需补安装器/发布”。

源码核对：[PC准备与复用](../Client/Assets/Editor/Build/PcQuickBuildUtility.cs)、[Android准备与复用](../Client/Assets/Editor/Build/AndroidQuickBuildUtility.cs)、[Windows指定版本发布](../Client/Assets/Editor/Build/WindowsInstallerPublishUtility.cs)。


## 第六项：生成安装器（PC）

入口：`Tools → 打包 → PC → 快速打包 → 生成安装器`。

适用情况：已有完整游戏目录，仅需补做或重新生成安装器。不会重新编译玩法、构建资源或游戏程序，也不会自动发布。安装器仍安装到当前Windows用户范围。

| 步骤 | 读取与输出位置、结果 |
|---|---|
| 1. 选择已有游戏 | 读取 `Client/Library/FirepowerLoopBuild/BuildState.json` 的最近成功PC游戏记录；记录指向的 `FirepowerLoop.exe` 仍存在时，默认打开其所在目录。否则打开 `Client/Build/Windows/`，尚不存在则回到最近的现存父目录（`Client/Build/` 或 `Client/`）。不使用Android记录、不自动选择游戏。手动选择EXE后读取同目录完整游戏文件，取消直接退出；此步不输出文件，也不修改成功记录。 |
| 2. 检查编译工具 | 读取本机 EditorPrefs 的 `FirepowerLoop.WindowsInstaller.Compiler`；没有可用文件时尝试 `%LOCALAPPDATA%/Programs/Inno Setup 6/ISCC.exe`，仍未找到再手动选择。检查文件存在且名称为ISCC.exe，成功后记住本机路径，不写仓库。 |
| 3. 检查并准备内容 | 执行仓库 `Tools/WindowsInstaller/build_installer.ps1`，读取所选游戏目录的核心文件、`FirepowerLoop_Data/StreamingAssets/windows-release.json` 与 `FirepowerLoop_Data/ScriptingAssemblies.json`；缺失或身份不符时停止。复制所需文件至 `Release/WindowsInstaller/Installer_<时间>_<随机标识>/payload/`，生成文件列表、校验信息和安装配置，并复制 `Tools/WindowsInstaller/FirepowerLoop.iss` 到该批次。 |
| 4. 生成安装器 | 在同一批次输出 `FirepowerLoop-Setup-<发布序号>.exe` 和 `app-update-windows.json`。更新清单记录安装器身份、大小和SHA256，供后续发布与下载校验；它不代表已经发布，也不是快速打包准备记录。序号沿用所选游戏，不因补做而递增。 |
| 5. 查看结果 | 成功后打开该批次目录；不会修改已有游戏、BuildState记录或资源服目录。文件检查不能替代游戏运行验收。 |

失败补做：游戏缺文件或版本信息不合法时，先找到完整的有效游戏目录；必要时通过现有打包入口重新生成游戏。编译工具有问题时修复ISCC配置后重试。安装器编译失败时，已有游戏与已创建的失败批次保留，再点本入口会建立新批次，无需重构游戏。若安装器已成功、仅发布失败，复用现有安装器按前文发布补做步骤处理，不必再次生成。

验证范围：本轮仅静态检查，未执行Unity编译、菜单运行、安装器生成或安装验证。


## 第七项：Android完整打包

入口：`Tools → 打包 → Android → 完整打包`。生成Development测试APK，内置完整资源，启动先联网更新，失败后尝试已成功缓存及内置资源；正式渠道入口另行处理。

| 步骤 | 读取、输出及用途 |
|---|---|
| 1. 环境检查 | 读取Client/ProjectSettings、Android SDK/NDK/JDK、本机签名配置及Client/Assets/StreamingAssets下hostConfig.json、networkConfig.json。必要时切换Android并等待重载；无正式产物。 |
| 2. 代码与AOT准备 | 读取Client/Assets脚本及HybridCLR配置，编译玩法至Client/HybridCLRData/HotUpdateDlls/Android；专用裁剪构建输出Client/HybridCLRData/AssembliesPostIl2CppStrip/Android，随后生成桥接及引用资料，复制代码资源至Client/Assets/Game/Dlls。已删除额外预备APK，必要的HybridCLR专用构建仍保留。 |
| 3. 完整资源 | 读取资源收集配置及工程资源，输出Client/Bundles/Android/DefaultPackage/<资源版本>/，并重写Client/Assets/StreamingAssets/yoo/DefaultPackage内置资源。 |
| 4. 保存准备记录 | 写Client/Library/FirepowerLoopBuild/AndroidQuickInputs.json及AndroidQuickAot下对应版本的不可变资料；用于失败后的快速复用核对，不表示APK已成功，也不自动续跑。 |
| 5. 最终APK | 读取已准备代码、资源与Boot，版本预留写Client/Library/FirepowerLoopBuild/AndroidVersionReservation.json；输出Client/Build/Android/<批次>/FirepowerLoop-<应用版本>.apk。检查实际APK资源与准备输入，再写BuildState.json中的Android成功记录，供后续热更新查找基线；这仍不代表发布成功。 |
| 6. 交付资料 | 读取Client/安卓联机玩家说明.md，复制到同一APK批次目录；清理本次临时目录。 |
| 7. 发布本次资源及APK | 明确读取第3步资源版本，将其同步到Release/ResourceServer/Android/<资源服批次>/ResourceFiles，并核对全部资源及清单；再将第5步APK发布到同一资源服批次的AppUpdates/Android，生成app-update.json。不会保留旧远端资源来搭配新APK；这是本机发布目录，不等于公网部署。 |
| 8. 启动提示 | 成功后可选择启动本地资源服；使用已发布目录，不重新构建游戏。 |

失败处理：

- 代码或资源准备未完成：修复明确报错，再完整打包。准备记录不可靠时不得强行复用。
- 准备成功、最终APK失败：本次未完成APK目录会清理；输入未变化时可用“复用全部打包”，已有记录不兼容则停止并提示重做。
- APK校验通过后，记录保存或说明复制失败：APK保留。先处理权限或缺失说明文件；成功记录不能根据文件名猜测，应由构建流程重新核验后保存。不要将此状态称为发布成功。
- 发布资源失败：APK和源资源保留。按失败日志的资源版本补做同步；现有“发布资源服/更新资源服”会选择最近资源，仅在它确实仍是本次版本时使用，否则需通过指定目录/版本的PublishOrUpdateAndroidPackage接口补做，不能盲目发布后来生成的版本。
- 资源已同步、仅APK发布失败：复用保留的APK，使用仓库Server/ResourceServer/publish_app_update.ps1，明确传入-Apk、-VersionName、-VersionCode和-Bundle。版本信息必须取该APK真实身份（可用Android SDK的aapt读取），不能取之后已变化的编辑器版本。脚本输出仍为该Bundle的AppUpdates/Android，并验证签名及文件完整性；当前没有单独APK发布菜单。
- 仅资源服启动失败：使用“Tools → 服务器 → Android → 启动资源服”，无需重建或重复发布。

本轮仅静态检查，未执行Unity编译、限定测试、实际APK构建、设备安装或资源服发布。完整包内部跨重载身份仍保留“Android 完整包”，避免旧待续跑记录失效。


## 第八项：Android启动包（首次下载资源）

入口：`Tools → 打包 → Android → 启动包（首次下载资源）`。生成Development测试APK，仅内置Boot与资源清单；首次安装无缓存时必须联网下载完整资源，断网不能直接进入游戏。适合希望减小初始APK、通过资源服提供内容的场景。

| 步骤 | 读取与输出位置、用途 |
|---|---|
| 1. 环境及网络检查 | 读取Client/ProjectSettings、本机Android SDK/NDK/JDK及签名配置、Client/Assets/StreamingAssets中的hostConfig.json和networkConfig.json。必要时切Android并等待重载；无正式文件输出。 |
| 2. 生成代码与AOT | 读取工程脚本及HybridCLR配置，玩法输出Client/HybridCLRData/HotUpdateDlls/Android，裁剪AOT输出Client/HybridCLRData/AssembliesPostIl2CppStrip/Android，代码资源复制到Client/Assets/Game/Dlls。保留专用裁剪构建，取消额外预备APK。 |
| 3. 生成远程资源与内置清单 | 读取资源收集配置及工程资源，完整资源输出Client/Bundles/Android/DefaultPackage/<资源版本>/；Client/Assets/StreamingAssets/yoo/DefaultPackage仅放清单与空内置目录，不放资源Bundle。 |
| 4. 保存准备记录 | 写Client/Library/FirepowerLoopBuild/AndroidQuickInputs.json及AndroidQuickAot下对应版本资料，标记启动包类型；供两种快速打包核对与复用，不代表APK已经生成，不自动续跑。 |
| 5. 构建并校验APK | 版本预留写Client/Library/FirepowerLoopBuild/AndroidVersionReservation.json，APK输出Client/Build/Android/<批次>/FirepowerLoop-<应用版本>.apk。检查实际APK资源及准备输入，通过后只保存一次BuildState.json中的Android成功记录，用于后续基线查找；尚未发布。 |
| 6. 复制说明 | 读取Client/安卓联机玩家说明.md并复制到APK同批目录，清理本次临时目录。CI在保存成功记录后归档明确版本的资源与APK并返回，保持不自动发布。 |
| 7. 发布匹配资源与APK | 读取第3步明确目录和版本，同步至Release/ResourceServer/Android/<资源服批次>/ResourceFiles；校验完整资源与同版本清单后，发布APK至该批次AppUpdates/Android并更新app-update.json。只写本地发布目录，不等于公网部署。 |

失败补做：准备阶段失败应修复报错再重做；准备完成但最终APK失败，输入未变时用“复用全部打包”，仍沿用启动包类型。APK验证通过后，即使保存成功记录、复制说明或发布失败也保留APK；先处理对应原因，不将已有APK误报为已发布。

资源同步失败时补做本次目录和版本的发布，不能因“最新资源”已变化而误发另一批；指定版本接口及已有APK发布脚本参数见第七项失败处理。仅APK发布失败可复用同一APK，不必重新生成；仅资源服启动失败使用“Tools → 服务器 → Android → 启动资源服”。未生成成功记录时，不能手填版本来冒认可热更新基线。

本轮仅静态检查，未执行Unity编译、限定测试、APK构建、首次下载或设备验收。内部跨重载身份继续使用“Android 启动包”，不影响旧待续跑记录。


## 第九项：Android构建热更新（代码+资源）

入口：`Tools → 打包 → Android → 构建热更新（代码+资源）`。适用于已有APK、仅更新可热更玩法代码或资源；不生成新APK，不更新应用版本。启动代码、插件、底层程序集、桥接、构建设置或新增原生调用不兼容时停止，要求重新完整打包或制作启动包并安装新APK。

| 步骤 | 读取、输出及检查 |
|---|---|
| 1. 绑定已有APK | 读取Client/Library/FirepowerLoopBuild/BuildState.json的LastAndroidPlayer及LastAndroidAotBaseline，检查记录指向的APK内容指纹、Boot指纹、资源版本和包型；APK通常在Client/Build/Android/<批次>/。不扫描最新文件推断成功。 |
| 2. 核对冻结资料 | 读取Client/Library/FirepowerLoopBuild/AndroidQuickAot/<APK对应资源版本>.json及同名目录；验证Unity版本、构建设置、非Game代码、插件、桥接及冻结文件。读取目录中的runtime-list.bytes与baseline-game.bytes，不使用工程中可被覆盖的当前名单。旧成功记录缺APK内容指纹时必须重新生成APK，不自动补填。此步不写文件。 |
| 3. 编译玩法 | 当前Game脚本编译至Client/HybridCLRData/HotUpdateDlls/Android/Game.dll；对照冻结的baseline-game.bytes检查外部托管引用及原生调用需求。通过后将Game及冻结AOT、名单复制到Client/Assets/Game/Dlls。 |
| 4. 构建远程资源 | 读取当前资源及上步代码，输出Client/Bundles/Android/DefaultPackage/<新资源版本>/；不重建APK或改内置资源。逐包核对完整远端内容，并在长流程结束后复核APK基线、手写输入和生成资料未变。 |
| 5. 保存生成结果 | 更新BuildState.json的Android最近资源/Host记录，不覆盖原APK及AOT基线。记录表示资源生成成功，用于后续查找，不代表发布完成，也不自动续跑。CI只归档该资源目录后返回，不发布。 |
| 6. 发布指定版本 | 仅同步第4步明确目录与版本至Release/ResourceServer/Android/<资源服批次>/ResourceFiles，随后对照构建时快照逐包核对发布内容；不发布新APK。 |
| 7. 启动资源服 | 从第6步目录自动启动本地资源服并探测本次版本；失败保留已生成与已发布资源。该目录为本机发布产物，公网部署另行处理。 |

失败补做：兼容性检查失败应重新生成并安装APK，不能篡改指纹绕过；Game编译或资源构建失败，修复后重新执行本入口。资源已生成而发布失败，保留日志中的确切目录和版本，使用指定目录/版本的PublishOrUpdateAndroidPackage接口补做；现有资源服菜单选择最新资源，仅在最新版本仍为本次版本时使用。发布后校验失败先修复资源同步，再核对完整文件，不将探测到版本号等同于完整资源有效。仅服务器启动失败使用Android“启动资源服”，无需重新编译资源。

本轮仅静态检查，未Unity编译、测试、真实热更新或设备验收。内部跨重载身份继续使用“Android Host 代码+资源更新”。


## 第十项：Android渠道打包

入口：`Tools → 渠道发行 → Android → 渠道打包`。用于准备联网渠道的正式签名候选APK：关闭Development与调试，检查正式环境及实际包。技术检查通过不代表真机验收或商店审核通过，不自动发布资源服或提交渠道。普通完整打包及两种快速打包属于内部测试流程，不能代替本入口。

| 1. 正式配置检查 | 从环境变量FIREPOWER_ANDROID_CHANNEL_SIGNING_CONFIG、FIREPOWER_ANDROID_CHANNEL_SIGNING_POLICY指定的本机文件读取正式签名配置和公开证书策略，不回退到测试证书。读取Client/Assets/StreamingAssets下hostConfig.json、networkConfig.json、diagnosticConfig.json，核对公网配置。缺配置先停止，不生成APK；不把私钥配置写入仓库。 |
